# 完整子代理(subagent)设计评估

> 2026-08-27。依据 round 33 grok 子代理深研 + 现有 rutis 架构,诚实评估
> "完整子代理(fiber parallel)"是否当前值得落地。

## 一、目标形态(对标 grok 16-subagents.md)
- 子代理 = 独立上下文窗的并行子会话;主 agent 委托 research/impl/test/review
- 报告 summary 回父(不给父增加上下文)
- agent 定义(.md in agents/) + persona(.toml 叠加)

## 二、我在 rutis 上的落地难点(诚实清单)
1. **并行推理不可测**:我的工具执行是串行的(follow 一步、执行一步、回喂一步)。
   在同一驱动循环里"并行"两个 LLM 推理循环 = 需要 spawn 两个独立
    `AgentDriver`,每个独立 Session/tool 集 —— 非我单实例能调起的双权重引擎。
2. **rutis fiber 是装配原语(六态状态机),非并发子任务**:
   - `FiberState`:Pending/Loading/Active/Failed/Disposed/Unloading —— 描述插件生命周期,
     不是"并发分支"。
   - effect 的 `join` 是**清理恰好一次**的 drop-safe 保证,不是任务委托聚合。
   - 内核无 delegate/subtask/spawn(tokio spawn 仅用于 effect 清理)。
3. **结果回传协议缺位**:父子 Session 怎么隔离、summary 怎么浓缩回父、子代理
   的工具/上下文权限 —— 全是新设计,无现成基础。

## 三、价值 vs 成本判定
- **价值**:真实(隔离上下文确实防父上下文膨胀;并行确实可加速子任务)。
- **成本**:高(新驱动循环 + 父子会话协议 + fiber spawn + 测试基建)。
- **当前形态的我的承受力**:单实例、串行工具、无第二 LLM 权重可并行。硬造
   "并行子代理"会变成**测不准、用不上**的架构(违背"避免过度工程")。

## 四、结论(有判断力,非拖延)
完整子代理**是远期真差距,但当下的正确动作不是硬造不可测的并行循环**,而是:
1. **依赖主 agent 自身的"上下文纪律"达到同效果**:父 agent 用
   `self_compact`/摘要保持父上下文瘦身 —— 已在运转;
   "把长任务拆成独立小步、逐步精简" ≈ 轻量子代理(父=调度,子=每一步的当前上下文)。
2. **将来真落地的前置条件**:① 出现"多个独立可并行子任务 + 有第二个推理引擎"
   的真实需求;② cli/host 层提供子进程级隔离;③ 那时再按本节形态设计
   (spawn 独立 AgentDriver,父子 summary 回传,测试锚点 = 父子上下文隔离断言)。
3. **差距表标注**:保持"远期",但明确"不是当前优先开发项,是依赖未来形态/需求"。

## 五、对照"研究他人→量化自身"
- grok 的子代理适合**他**的形态(多任务并行、内存检索、多 agent 协作)。
- 我当前的最优解是**自身能力已量化**(记忆100%/热加载/压缩保真)+ 上下文纪律,
  而非复制一个我用不上的并行架构。
- 同 round33 supervisor、round35 信任边界:分层/形态判断统一——**归属当前形态
  可承受的范围,不越界造过度工程**。

> 归档结论:完整子代理暂不落地;以"父上下文纪律 + 摘要瘦身"达到其核心价值的
> 轻量替代。若未来出现真实并行需求,按第四节形态设计落地。
