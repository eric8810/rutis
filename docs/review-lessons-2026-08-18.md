# 评审方法论与领域规律沉淀

> 2026-08-18。来源:zcode 对整个 min-cordis Rust 移植评审过程(design v4→v5、实现评审、简化评审共五轮)的提炼,Dim 核对全部属实后整理成文。
> 性质:方法论 + 领域规律,非施工清单。施工内容见 [simplify-conclusion-2026-08-18.md](simplify-conclusion-2026-08-18.md)。
> 每条附本项目具体证据,避免方法论落空。

## 一、简化的判据不是"少",是"同一事实说了几遍"

冗余的正确定义:**一个事实有两个真相源,外加一条让它们保持同步的义务。** 同步义务才是 bug 产地。

判别工具只有一个问句:**"这个机制在回答什么问题?"** 同一问题被回答两遍,删一个;问题不同,哪怕长得一模一样也不许动。结构体数量、行数、泛型参数个数,都不是判据。

本项目证据:

| 真冗余(同一问题答两遍) | 假重复(看着像,其实问题不同) |
|---|---|
| 反向索引 reverse map 与 `last_deps`(同一依赖集合) | status_queue 与 watch(全量有序历史 vs 最新值) |
| `resolved` 旗标与 `intents_inflight`(都答"前序工作完成没") | 两个 watch channel(一次性完成的 identity vs 连续状态流) |
| once 的 `fired` 原子标志与总线锁(同一份串行性) | — |

## 二、删除的所有权测试:能说出它当时挡住了什么

每一项删除候选,必须能配对说出"它当初挡住了哪个竞态/哪个坑"。**说不出来,就还不拥有这次删除。**

方向是判断,红线是所有权。四条施工红线全是这个形态:设计方向都对,翻车点全在没写出来的不变式上——Settle 只认 Failed 回传错误、once 删除必须保快照原位、删 yield 协议要封退出竞态。

本项目证据(反面):Dim 提议删 status_queue、合并两个 watch channel,都是说不出它们挡着什么就被"看着像重复"带偏,后经测试证据纠正。

## 三、串行队列系统的等待问题,答案在队列里,不在旁路信号里

"我之前提交的事干完了没有"——如果执行者是串行 mailbox,这个问题应该由**在队列里排一个哨兵意图、join 它**来回答,而不是在外面用计数器、旗标、双重检查去反推。

凡是 actor/mailbox 模型的系统,先检查你在等待侧搭了几层旁路推理。

本项目证据:settle 用五个外部信号拼(`resolved`/`intents_inflight`/`notify_inflight_drained`/watch 双检/`drain_stale` 的 yield),理论上一个 `Intent::Settle(TransitionTask)` barrier 全替掉。

## 四、修 bug 修出来的复杂度是疤,不是脂肪;审自己的疤,先查自己的病历

评审一个形状是否多余之前,先查构建史和 git log——你为修某个错而加的形状,几个月后会误记成累赘。

配套:**同一段正确的代码被多个独立评审者反复误读,是代码本身的缺陷。** 可读性是正确性的邻近属性,为"一眼看懂"重写也算简化,哪怕行数不变。

配套动作:修坑的当时就把"承重墙条目"写进文档,别等简化时凭记忆辩护。

本项目证据:

- zcode 提议删三个 Adapter 的 PhantomData,说是"怪形态"——忘了本项目第一天就撞过 E0207(unconstrained type parameter),PhantomData 正是当时的修法。
- serial 那段 JoinSet 写法(循环体内 spawn 第 i 个 → 立即 join_next → 才 spawn 第 i+1 个)被 Dim、Mira 两轮误读为"并发分发",被迫重写为内联顺序 await——语义没变,但"一眼可见是串行"。

## 五、多评审员协作的实际规律

**收敛处是铁案,分歧处是判断题,误读重复出现是信息。**

- 收敛处不用再议:四个独立评审员对阻断项的判断几乎全同。
- 分歧处按项目初衷裁决:分歧集中在"可辩护项的激进/保守取舍",那是偏好不是对错(本项目初衷"非必要不动")。
- 验证分歧断言靠**物证**(API 文档、构建记录),不靠对自己记忆的自信:codex 指出 Adapter 毯式实现不成立,zcode 查了 tokio 文档和本项目历史后确认它对,包括确认"我错"。

## 六、领域规律:协作取消遇到串行驱动者,取消动作必须由发送方在入队前执行

生命周期框架 / actor 系统特有。驱动者串行处理意图,永远轮不到"边执行边自我取消";让 apply 观察到取消的唯一时机,是**意图发送方先取消再排队**。

本项目证据:代码里 `dispose()`/`restart()` 在 `post(Intent::...)` 入队前先 `cancel_current()`([fiber.rs:652](../crates/rutis/src/fiber.rs#L652)、:678)。死锁了一轮才看明白这一点——若不预取消,驱动串行,apply 永远等不到取消信号。
