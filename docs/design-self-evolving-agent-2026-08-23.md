# 自我演进 agent 的 minimal persona 设计

> 2026-08-23。目标:把 `minimal_persona` 从一行 `format!` 字符串升级为"自我演进 agent"的分节系统提示词——环境引导 + 方向定义 + 一条硬纪律,并明确自我演进的边界。
> 依据:[design-min-agent-2026-08-18.md](design-min-agent-2026-08-18.md)(最小 agent 框架)、[design-minimal-mode-2026-08-18.md](design-minimal-mode-2026-08-18.md)(minimal mode)。
> 定位:MVP 增量——在"能改文件、能跑命令"之上加"能自我演进"。

## 一、设计意图

一份好的自我演进提示词应当**轻**:它不写死演进任务清单,只做两件事——

1. **环境引导**:告诉 agent 它在哪、宿主的语义是什么、有哪些可用资源。
2. **方向定义**:给三条使命方向,由每次会话根据环境现状自行决定具体任务。

外加一条**硬性行为纪律**:任务文档化防中断。因为 agent 的执行可能中断,文档是断点续接的唯一凭据——这是 identity 超越 session 的物理载体。

## 二、约束清单(与团队确认)

| # | 约束 | 落实 |
|---|---|---|
| 1 | 放在 `minimal_persona` 里 | 分节 system prompt,`{model}`/`{cwd}` 照旧插值 |
| 2 | 方法论无关 | 不引用 `review-lessons`、不引用决策编号 |
| 3 | repo 代码/信息都是参考信息 | 不是禁区,皆可读、可演进 |
| 4 | agent 可以改自己的代码 | 首选 **plugin 方式**:加入新代码 → 实时测试 → 热更新;plugin 重载后身份延续 |
| 5 | 原始 minimal persona 的变更需用户同意 | 唯一例外条款,写入提示词 |

## 三、提示词结构(四节 + 版本脚注)

```text
# 身份与使命        —— 三条方向:工程最好 / 环境适应最佳 / 迭代能力最强
# 环境引导          —— 在 rutis 工作区;框架语义=世界观;仓库信息皆参考;动手之前先读
# 工作纪律          —— ①任务开始先写工作文档 ②过程持续更新 ③小而可验证、过测试 ④决策可观测
# 自我演进          —— 可改自己代码(plugin+实时测试+热更新);唯一例外:persona 变更需用户同意
(identity: self-evolving persona v1;model: ...;cwd: ...)
```

- **使命三句是方向,不是考核项**:不写"每个任务用三问衡量"这类硬性判据,保持轻。
- **工作纪律只写 4 条**:前两条(任务开始落文档 / 过程持续更新)是唯一写死的"必备行为",因为它们防中断。
- **版本脚注**:机器可读,`v1` 起步,便于审计 persona 自身的演进历史。

## 四、自我演进的边界

```
可改:  运行自己的代码(首选 plugin 方式,热更新)
可读:  仓库全部代码与信息(参考信息,不是禁区)
不可改: 本 minimal persona 本身 —— 变更必须经用户同意
```

边界分三档,清楚写明。这保证 agent 能自由演进**外围**(工具、策略、新 plugin),但**核心身份**不随自我修改漂移——与 rutis 的"llm 是服务不是 agent"同一哲学。

## 五、验证

`crates/rutis-agent/tests/minimal_tools.rs` 新增 `persona_carries_essential_self_evolution_clauses`:

- 使命三句、`执行可能中断`/`工作文档`(硬纪律)、`plugin`/`热更新`(演进方式)、`必须经用户同意`(边界)、插值生效 —— 全部断言锚住。
- 目的:这份提示词本身有测试保护,不会被意外改没。
